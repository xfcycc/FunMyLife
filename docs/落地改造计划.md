# Life Manager 落地改造计划

## 1. 当前底座

当前项目包含：

- `admin-web`：Vue 3 + TypeScript + Vite + Soybean Admin + Naive UI。
- `fml-service`：独立 Life Manager 轻量后端，Spring Boot 3.5，JDK 21，MyBatis-Plus，MySQL。
- `admin-service`：RuoYi-Vue-Plus 5.6.1 后台底座，保留系统管理、OSS、SSE、任务调度、Docker 脚本等历史能力。

虽然最初设想是 React，但当前 Vue 底座已经覆盖了大量前端工程能力。后端已从过重的后台管理系统中拆出，后续 Life Manager 业务接口优先以 `fml-service` 为事实源。

## 2. 改造原则

1. Life Manager 业务接口优先进入 `fml-service`，不再继续加重 `admin-service`。
2. 删除或隐藏无关演示页面，避免后台味太重。
3. 必要的后台能力保留在 `admin-service`，后续按需要再做轻量接入或替换。
4. 先做项目视角，再补完整功能视角。
5. 工作台优先改成产品型仪表盘，而不是传统数据看板。
6. 敏感信息第一版就按安全要求处理，不先明文凑合。

## 3. 保留能力

`fml-service` 当前承接：

- 项目基础信息
- 功能块实例配置
- 能力注册与概览摘要
- 无限暖暖目标、版本活动、素材、图册、资产、笔记、时间轴、AI 摘要占位接口
- 统一 `POST + JSON body` 接口协议

`admin-service` 暂时保留：

- 系统管理能力
- OSS 文件能力
- SSE 推送能力
- 任务调度和监控能力
- Docker 依赖脚本
- 历史 SQL 与管理后台参考实现

前端保留：

- 基础布局
- 登录页
- 菜单渲染
- 权限路由
- Naive UI 组件体系
- 主题能力
- 表格、表单、上传等公共组件
- SSE 客户端工具
- OSS 上传组件

## 4. 需要弱化或隐藏的内容

第一阶段可以隐藏：

- 租户管理
- 租户套餐
- 部门管理
- 岗位管理
- 工作流
- 监控页面
- 缓存页面
- 在线用户
- 代码生成入口
- Demo 页面
- 关于页面

这些能力不是删除，只是不作为 Life Manager 的主界面出现。后续需要时可以在设置或开发者区域恢复。

## 5. 业务模块规划

第一批主导航建议改成：

- 工作台
- 项目
- 待确认
- 设置

日程、清单、记录、资产、图册、AI 助手这类内容不再默认平铺为主导航。它们是功能块或能力，应该根据项目类型和项目方案进入项目内部 tab、概览摘要、时间轴或项目管理页配置。系统管理相关页面可以放到“设置”或“系统设置”里。

## 6. 第一阶段目标

第一阶段目标是把底座从“若依后台”变成“Life Manager 产品雏形”。该阶段的静态产品壳已经基本完成，当前重点转为独立后端联调收口。

已完成：

1. 系统品牌替换为 Life Manager。
2. 默认入口替换为 Life Manager 工作台。
3. 新增项目管理页面。
4. 新增项目内部概览页面。
5. 新增项目管理配置页面。
6. 菜单调整为 Life Manager 的信息架构。
7. 保留系统管理能力，但弱化入口。

当前已新增 `fml-service` 独立后端，并将无限暖暖项目页的一批接口切到真实 HTTP 请求。后续不再按“纯静态壳”推进，而是以“前端页面 + `fml-service` 数据闭环”为验收标准。

本文“第一阶段”更偏产品形态和静态演示，对应需求文档 MVP 的前半段。需求文档 MVP 中的待确认收件箱基础流程和 AI 摘要，在本计划里进入第二阶段继续补；两者不矛盾，先稳定产品壳，再补业务闭环。

## 8. 第二阶段目标

第二阶段目标调整为 `fml-service` 真实联调收口。

项目类型、方案和功能块实例配置应优先按 [Life Manager 方案模板协议.md](./Life%20Manager%20方案模板协议.md) 落地。当前先保证无限暖暖能用 `fml-service` 跑通，再用日本旅行验证同一套协议是否可复用。

优先顺序：

1. 按 `fml-service/README.md` 跑通启动方式、数据库初始化和本地前端代理配置。
2. 用 `lm_life.sql` 初始化 `fml` 库，验证 `fml-service` 能独立启动并返回无限暖暖数据。
3. 跑通无限暖暖项目页和管理页真实联调，确认目标进度、功能块实例批量保存、概览摘要可用。
4. 为项目详情、目标更新、功能块实例保存补最小测试。
5. 新增项目列表和工作台真实接口，减少首页与项目页 mock 数据。
6. 再扩日本旅行后端模型，验证同一套项目/功能块/方案协议的复用性。
7. 最后接入 OSS、AI、SSE 和外部通知。

第二阶段完成后，无限暖暖主链路不再依赖静态假数据，项目列表和工作台至少具备真实摘要入口。

## 9. 第三阶段目标

第三阶段做自动化和智能能力。

包括：

- SSE 实时推送
- AI 自动总结
- AI 今日建议
- 飞书提醒
- OpenClaw 联动
- Webhook
- MCP 查询和创建能力

## 10. 建议执行顺序

1. 跑通 `fml-service` 编译、数据库初始化和本地启动。
2. 将 `admin-web/.env.dev.local` 指向当前要联调的 `fml-service` 地址。
3. 验证无限暖暖项目页和管理页真实接口。
4. 补 `fml-service` 最小测试。
5. 补项目列表和工作台真实接口。
6. 复制同一套协议到日本旅行项目。
7. 接入 OSS、AI、SSE。
8. 做 Docker 部署收口。

## 11. 当前风险

1. 根文档和接口文档容易滞后于 `fml-service` 的真实协议，需要把文档改成跟代码同源。
2. 前端本地覆盖文件可能仍指向远程后端或旧后台端口，联调前必须确认 `VITE_SERVICE_BASE_URL`。
3. `fml-service` 目前缺少测试和 Dockerfile，初始化 SQL 仍复用 `admin-service` 历史脚本，交付闭环还不完整。
4. 第一版如果同时追求完整后端、完整 UI、AI、OSS、MCP，会范围过大。

## 12. 当前建议

先做 `fml-service` 收口，让系统真的跑在轻量后端上。

当前最应该完成：

- `fml-service` 独立启动验证
- 无限暖暖真实接口联调
- 最小测试保护
- 项目列表和工作台真实数据入口

这一步完成后，再继续扩日本旅行、AI、OSS 和 Docker 部署会更稳。
